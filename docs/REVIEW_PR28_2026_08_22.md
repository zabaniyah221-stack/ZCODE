## BLOCKER 1 — TransactionManager masih dapat menghancurkan environment lama sebelum commit

**Severity:** CRITICAL / data-package integrity
**Status:** REGRESSION/BUG CLASS MASIH ADA
**File:** `TransactionManager.kt` lines 123–161

Source exact:
https://github.com/muzape28-blip/ZCODE/blob/abf808da3b9b2f46af53dfa9936307dbe900f2e8/app/src/main/java/com/zaba/zcode/core/packageengine/TransactionManager.kt#L123-L161

PR body mengklaim pre/post commit sudah dipisahkan. Implementasi aktual:

```kotlin
val target = File(sitePkgs, p.canonicalName)
if (target.exists()) target.deleteRecursively()   // environment aktif hilang
versionDir.copyRecursively(File(target, p.version), overwrite = true)
...
// installed.json baru ditulis sesudah semua itu
```

Jika copy package kedua gagal, storage penuh, permission error, process death,
atau state write gagal:

```text
old package directory sudah dihapus
→ rollback memulihkan installed.json lama
→ JSON lama menunjuk directory yang sudah hilang
```

`runCatching { onLog(...) }` hanya mencegah callback melempar. Itu **tidak
menciptakan transaction boundary**.

Lebih buruk, rollback melakukan:

```kotlin
moved.forEach { it.deleteRecursively() }
```

lalu memulihkan backup JSON, tetapi tidak punya backup directory package lama.
Jadi istilah “rollback” tidak sesuai kenyataan.

### Kenapa guard hijau tidak membuktikan fix

Test baru hanya mencari string:

```python
assert "runCatching { onLog(" in tx
assert "runCatching { tx.dir.deleteRecursively() }" in tx
```

Test tersebut hijau sementara destructive pre-commit delete masih ada. Ini
adalah guard palsu menurut aturan proyek.

### Fix wajib

Gunakan generation path unik seperti fondasi PR #27:

```text
copy staging → .incoming generation
→ verify tree
→ atomic promote ke unique final generation
→ atomic installed.json commit
──────────── COMMIT BOUNDARY ────────────
→ cleanup old generation/log/journal best-effort
```

Kegagalan pre-commit hanya boleh menghapus generation baru yang belum dirujuk.
Post-commit tidak boleh menghapus generation aktif.

### Test wajib

Runtime/fault-injection test, bukan lexical-only:

1. package lama aktif;
2. package baru dipromote ke generation unik;
3. inject failure sebelum state commit → old path dan state tetap valid;
4. inject `onLog`/cleanup failure setelah commit → new state/path tetap valid;
5. process/copy/state failures tidak pernah menghasilkan JSON dangling;
6. mutasi kembalikan `target.deleteRecursively()` pre-commit → test RED.

## BLOCKER 2 — queued save masih dapat lolos lock dan menghidupkan file kembali

**Severity:** HIGH / user data correctness
**Status:** BUG MASIH REPRODUCIBLE SECARA SCHEDULING
**File:** `WorkspaceViewModel.kt` lines 461–563

Source exact:
https://github.com/muzape28-blip/ZCODE/blob/abf808da3b9b2f46af53dfa9936307dbe900f2e8/app/src/main/java/com/zaba/zcode/WorkspaceViewModel.kt#L461-L563

Inactive-file path:

```kotlin
val shouldSave = synchronized(workspaceMutationLock) {
    filename in openedFiles && revision/draft cocok
}
if (shouldSave) {
    FileManager.saveFile(...) // write terjadi SETELAH lock dilepas
}
```

Race yang masih legal:

```text
save job ambil lock
→ shouldSave = true
→ save job melepas lock
→ Clear/Delete/Rename ambil lock, invalidasi dan hapus file
→ mutation melepas lock
→ save lama menulis file
→ file hidup kembali
```

Active flush juga punya pola sama:

```kotlin
val isOpened = synchronized(lock) { ... }
// lock lepas
FileManager.saveFile(...)
```

`saveJob?.cancel()` tidak cukup. Cancellation coroutine bersifat kooperatif dan
job yang sudah melewati check atau sedang blocking file I/O tidak otomatis
mundur.

### Kenapa guard hijau tidak membuktikan fix

Test baru hanya memastikan:

- lock ada;
- revision map ada;
- kata `invalidateRevision` muncul;
- kata `capturedRev` muncul dalam potongan source.

Tidak ada barrier/fake writer, tidak ada actual interleaving, dan tidak ada
assertion bahwa **check + disk write berada dalam critical section yang sama**.

### Fix wajib

Minimal:

```text
capture documentId + revision + code
→ acquire workspace mutation lock
→ recheck identity/revision/draft
→ lakukan disk write sambil mutation lock masih dimiliki
→ release lock
```

Atau pindahkan filesystem mutation ke owner/dispatcher serial tunggal dengan
operation IDs. Jangan menggunakan check-then-act di dua critical section.

### Test wajib

Deterministic barrier:

```text
queue save
→ tahan worker tepat sebelum write
→ Clear/Delete/Rename commit
→ release worker
→ old file tidak muncul
```

Test harus meliputi active dan inactive saves serta tidak menggunakan `sleep()`.

## BLOCKER 4 — Verifier RECORD fail-open pada beberapa bentuk input tidak valid

**Severity:** HIGH / untrusted wheel supply chain
**File:** `Verifier.kt` lines 109–215

Source exact:
https://github.com/muzape28-blip/ZCODE/blob/abf808da3b9b2f46af53dfa9936307dbe900f2e8/app/src/main/java/com/zaba/zcode/core/packageengine/Verifier.kt#L109-L215

PEP 427:
https://peps.python.org/pep-0427/

Temuan:

### A. CSV diparse dengan `split(",")`

`RECORD` adalah CSV. Quoted filename yang mengandung comma tidak diparse benar.
Ini dapat menolak wheel valid atau membaca kolom yang salah.

### B. Hash non-SHA256 diterima tanpa verifikasi

Kode hanya memverifikasi bila:

```kotlin
expectedHash.startsWith("sha256=")
```

`md5=...`, `sha1=...`, `garbage=...`, atau hash kosong tidak ditolak; loop
langsung lanjut dan akhirnya sukses.

### C. Hash/size kosong diterima untuk file biasa

Untuk file bukan RECORD/signature, `expectedHash == null` dan
`expectedSize == null` tetap dapat berakhir `ok=true`.

### D. Size malformed diterima

`toLongOrNull()` menghasilkan null, lalu check dilewati. Nilai `abc` seharusnya
invalid, bukan “size tidak tersedia”.

### E. Duplicate RECORD path ditimpa

`recordEntries[path] = ...` mengganti row lama tanpa reject duplicate.

### F. Phantom RECORD rows tidak diperiksa

Kode memastikan setiap actual file punya row, tetapi tidak memastikan setiap row
menunjuk actual file. RECORD dapat mencantumkan file yang tidak ada dan tetap
lulus.

### G. Multiple `.dist-info` diterima

Kode mengambil `distInfos.first()`. Wheel seharusnya punya identity metadata yang
jelas; multiple candidates harus fail closed.

### H. Identity plan dan WHEEL version tidak diperiksa

Tidak ada expected package/version comparison dan tidak ada validation
`WHEEL/Wheel-Version`. Wheel yang metadata-nya tidak sesuai resolved plan dapat
lolos layer ini.

### I. Extraction hardening dari PR #27 hilang

PR #28 tidak membawa:

- max extracted bytes/decompression-bomb guard;
- max entry count;
- max entry-name length;
- duplicate ZIP entry rejection.

### J. Tidak ada runtime JVM unit fixture

PR #28 menambahkan lima string assertions, bukan `VerifierTest`. Tidak ada
fixture valid signed wheel, invalid hash, weak hash, comma CSV, duplicate row,
phantom row, arbitrary unlisted file, atau signature exception.

### Fix wajib

Mulai dari verifier PR #27 yang lebih ketat, lalu perbaiki gap signed wheel:

- parse CSV benar;
- exact one `.dist-info`;
- validate `METADATA`, `WHEEL`, identity, version;
- hash SHA-256/SHA-384/SHA-512 saja;
- all non-exempt files wajib hash/size sesuai contract;
- actual files dan RECORD rows harus setara **setelah** exception sempit untuk
  `RECORD.jws`/`RECORD.p7s` yang memang boleh absent dari rows;
- arbitrary unlisted files tetap ditolak;
- unit fixtures + mutation proof.

## MAJOR 10 — Delete flow dapat mengubah topology walau disk delete gagal

**Severity:** MAJOR / state-disk divergence

